夜幕、票根与一束光

本页记录视觉系统的原创决策与后端一致性设计：改期身份、容量处置、天气预案、席位并发与通知幂等。

一、视觉概念

露天电影的核心体验是「黑暗中的一束光」。界面因此以深夜蓝为天幕，琥珀色为放映机的暖光， 场次卡片设计为可撕下的票根——左侧深色票联印日期，与右侧票面之间以虚线压齿孔分隔； 取消的场次盖上褪色的 CANCELLED 印章，如同被窗口盖了作废章的纸质票。

字体排印

三套字族分工明确，全部使用系统字体栈，离线可用：

  • 衬线展示体（Songti SC / Noto Serif / Georgia）：片名、标题——电影海报的书卷气；
  • 等宽体（SF Mono / ui-monospace）：时间、票号、座位号——像放映机上的计数器，数字对齐便于扫读；
  • 无衬线正文（PingFang / Segoe UI）：说明性文字，保证小字号可读性。

布局

  • 票根卡片：86px 票联 + 自适应票面 的双栏网格，悬停上浮 3px 模拟从票夹中抽出；
  • 座位图：排号 + 圆角席位，银幕以一道下弯的琥珀光弧表现（border-radius 50% + 投影）；
  • 状态即信息：改期（原时间→新时间）、取消（褪色+印章）、满额（红色余票条）在列表首屏直接可读，无需点进详情。

二、领域设计：改期不是重建

改期被建模为同一活动的新排期版本：screenings.id 终身不变， 每次改期向 schedule_revisions 追加一行并前移 current_revision_id 指针。 票永远外键指向 screenings.id，因此无论改期多少次，原预约都不会失联； 查票接口始终返回「当前排期」时间。

screenings (id 恒定, current_revision_id ──┐
  version 乐观锁, capacity, taken_count)    │
schedule_revisions (screening_id, rev_no, ◄─┘
  starts_at, ends_at, ticket_policy)
tickets (screening_id ──► 活动身份, revision_id ──► 购票/迁移到的版本)

旧票处置由显式政策决定，逐票生成通知任务：

政策行为适用
migrate_all全部票自动指向新排期，状态保持 confirmed时间微调，观众大概率接受
opt_in票转 migrate_pending，观众在页面确认/退票；席位继续为其保留时间变化大，需观众同意
void_all全部作废、释放席位、通知退款重报活动性质改变

三、容量缩减：保留顺序，明示处置

每张票确认时获得场次内单调递增的 confirm_seq。缩减容量时按 confirm_seq ASC 保留先到者，超出者进入 displaced（席位释放、生成处置通知），接口把需处置人群名单 按顺序返回给运营——绝不随机撤销。扩容时按同一顺序尝试恢复 displaced 票，且仅在原座位仍空闲时恢复，不挤占他人。

四、天气预案：数据不直接改公开状态

观测注入 ──严重?──► 匹配场次(场地+时间窗) ──► 有 pending 预案? ──是──► 更新触发数据(仍待决定)
     │                                      └──否──► 已有决定? ──否──► 新建 pending_decision 预案
     │                                                  └──是──► 观测时间 ≤ 决定时间? ──是──► ignored_stale
     ▼ 否                                                            └──否──► 新建 pending(新证据)
  仅记录观测
运营 decide(approve) ──► 才改变 screenings.status（公开状态）＋ 作废票 ＋ 通知

迟到的观测（observed_at ≤ decided_at）不会推翻既有决定；场次已终态时后续观测记为 ignored_terminal。所有忽略都写入 weather_events 审计表，可在后台查看。

五、席位并发：全场次锁 vs 席位原子占用

系统实现了两种可切换策略（环境变量 BOOKING_STRATEGY），共享同一套 SQL 不变量：

维度全场次锁 screening_lock席位原子占用 atomic（默认）
互斥粒度整个场次：进程内互斥锁 + SELECT 校验后插入单个席位：seat_occupancy 主键冲突即失败
容量控制锁内读 taken_count 判断条件 UPDATE 原子递增（taken_count < capacity 才 +1）
竞争失败影响同场次所有下单互斥，失败波及不相干席位仅冲突席位失败，其余席位并行无阻
吞吐低（串行），热点场次明显高，失败率与席位热度成正比而非场次热度
可迁移性依赖应用层锁，多实例部署需分布式锁纯数据库约束，可直接平移到 Postgres 行级唯一索引
适用需要跨行不变量（如“每场最多 N 张联票”）时更直观常规选座预订，配合唯一索引即可证明正确

正确性不依赖策略选择：seat_occupancy(screening_id, seat_id) 主键是席位占用的唯一裁决者， 占位与出票共用此表（occupant_type = hold / ticket）。测试在两种策略下各跑一遍「最后席位竞争」： N 个并发请求抢同一座位，恰好 1 个成功。

预留超时与改期中的报名约束

  • 占位写入 seat_holds（含 expires_at），读取路径惰性清扫 + 服务端定时清扫回收席位与计数；
  • 改期事务开始时将 sale_state 置为 paused，结束恢复 open；暂停期间新报名一律 409。 由于改期是单事务，外部只会看到原子切换；运营也可手动暂停售票（如评估改期方案时）；
  • 确认出票要求占位仍 active 且场次 scheduled——占位超时后再确认返回 409。

六、通知中心与幂等

  • 通知任务以 idempotency_key（类型:场次:票）去重，重复改期/取消不会产生重复任务；
  • 派发走本地模拟渠道：写入 mock_outbox（task_id 唯一），后台「模拟渠道」页可查看发件箱并手动回执；
  • 回执以 UNIQUE(task_id, receipt_token) 幂等：重复回执返回 duplicate:true，不重复登记、不重复改状态。

七、版本与防旧响应覆盖

  • 服务端：screenings.version 乐观锁，管理端写操作须携带读到的版本号，失配返回 409 VERSION_CONFLICT 与当前版本，前端收到后自动刷新重试提示；
  • 浏览器：js/guard.js 为每次请求发递增令牌，响应到达时若已有更新响应被应用则丢弃； 行级再按 version 防回退——乱序到达的旧响应永远不会覆盖页面上的新状态。
